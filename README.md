# OHM Monitoring: Prometheus and Grafana

This repository installs **Prometheus**, **Grafana** and exporters to monitor the **OpenHistoricalMap** infrastructure. 

## Install

Installs into the `monitoring` namespace:

- **Prometheus** (server, alertmanager, node-exporter, kube-state-metrics, pushgateway), 30d retention. Its data and Grafana's live in fixed folders on the node labelled `nodegroup_type=downstream`: `/mnt/prometheus-data` and `/mnt/grafana-data` (`manifests/volumes.k3s.yaml`), so they survive moving the node to another cluster.
- **Grafana** with the Prometheus datasource and the dashboards from `dashboards/` provisioned automatically.
- Alert rules for pods (CrashLoop, NotReady, OOMKilled) and nodes (NotReady, disk), plus a `Watchdog` heartbeat. External site up/down checks are handled by UptimeRobot, not here. See issue [#1000](https://github.com/OpenHistoricalMap/issues/issues/1000).

### Deploy

```sh
cp .env.example .env   # fill in credentials (gitignored)
./deploy_k3s.sh create
```

Quick check without exposing anything:

```sh
kubectl port-forward svc/grafana 3000:80 -n monitoring
kubectl port-forward svc/prometheus-server 9090:80 -n monitoring
```

### Exposing Grafana through the Cloudflare tunnel

- `monitoring.openhistoricalmap.org` → Type `HTTP` → `grafana.monitoring.svc.cluster.local:80`

Then point the `monitoring.openhistoricalmap.org` DNS record to the tunnel. Do not expose Prometheus or Alertmanager without auth; keep them on port-forward, or add a tunnel hostname protected by a Cloudflare Access policy.

## Usage stats: requests, people and client apps

Issue [#1412](https://github.com/OpenHistoricalMap/issues/issues/1412). Traffic enters through the Cloudflare Tunnel straight into ClusterIP services, so there is no ingress layer that could count requests. The Cloudflare GraphQL Analytics API (available on the Free plan) is the one place that sees every request across EKS and Hetzner, so a CronJob pulls the numbers from there.

`cloudflare-stats/cronjob.yaml` runs every hour in `monitoring` and pushes to the Pushgateway. It does not depend on which cluster hosts Prometheus, only on the Pushgateway being there. Prometheus scrapes it and three dashboards show it (generated by `dashboards/gen_cloudflare_dashboards.py`):

| Dashboard | Question it answers | For |
|---|---|---|
| **OHM usage** | How many people use OHM? How much is each tool used? How do editors reach the API? | Jeff, the community |
| **OHM clients** | Which apps, browsers, scripts and bots send the traffic, per tool? Bot share, HTTP methods. | maintainers |
| **OHM traffic health** | Hourly load, blocked (403) and error (5xx) requests, Cloudflare cache hit per host, live tunnel rate, stats job status. | operations |

| Metric | Meaning |
|---|---|
| `ohm_cf_host_visits_daily{host}` | **people**: browser sessions per hostname from Cloudflare Web Analytics (JS beacon). Use `host="www"`: ~93% of beacon hits on this zone come from headless browsers scraping HTML pages on `api.*`, not from people. |
| `ohm_cf_visits_daily`, `ohm_cf_visits_hourly` | Web Analytics sessions for all hosts, scrapers included |
| `ohm_cf_pageloads_daily` | page loads from Web Analytics |
| `ohm_cf_requests_daily`, `ohm_cf_requests_hourly` | all requests for the whole zone (tiles, API, JOSM, bots), exact |
| `ohm_cf_uniques_daily`, `ohm_cf_uniques_hourly` | unique client IPs, whole zone, includes bots. Hourly values do not add up. |
| `ohm_cf_host_requests_daily{host}` | requests per hostname, sampled estimate. Host labels are short: `www`, `api`, `vtiles`, `nominatim`, ...; the bare domain keeps its full name `openhistoricalmap.org` |
| `ohm_cf_host_unique_ips_daily{host}` | distinct client IPs per hostname. Sampled, so a lower bound: Free has exact uniques only for the whole zone. IPs are counted in the job, never stored. |
| `ohm_cf_agent_requests_daily{agent}` | requests per client app, classified from the User-Agent: `JOSM`, `QGIS`, `browser:Chrome`, `python-requests`, `bot:Google`, ... |
| `ohm_cf_method_requests_daily{method}` | requests per HTTP method. `PUT`/`POST`/`DELETE` on `api` are edits, `GET` is reads and tiles. |
| `ohm_cf_status_requests_daily{status}` | requests per edge response status: `200`, `404`, `429` (rate limited), `5xx` (origin errors) |
| `ohm_cf_host_agent_requests_daily{host,agent}` | requests per hostname and client app |
| `ohm_cf_host_method_requests_daily{host,method}` | requests per hostname and HTTP method |
| `ohm_cf_host_cache_requests_daily{host,cache}` | requests per hostname and Cloudflare cache status (`hit`, `miss`, `expired`, `dynamic`, ...). For `vtiles`, hit ratio = tiles served without touching Martin. |
| `ohm_cf_cached_requests_daily` | requests served from the Cloudflare cache |

Bot Fight Mode stays **off**: it blocks older editors and scripts. Bots are separated by the User-Agent classifier and by Web Analytics instead.

Setup in Cloudflare (dashboard, no impact on traffic):

1. **Web Analytics**: Analytics & Logs → Web Analytics → Add a site → pick the zone → automatic setup. Cloudflare injects the beacon `<script>` into HTML pages only. Without this the `ohm_cf_visits_*` metrics are skipped.
2. **API token**: My Profile → API Tokens → Create → permission *Zone / Analytics / Read* on the zone. Put `CF_ANALYTICS_API_TOKEN` and `CF_ANALYTICS_ZONE_ID` (zone Overview page) in `.env`.
3. Optional `CF_ANALYTICS_S3_URI` + AWS keys also write one JSON per run to S3, since Prometheus keeps 30 days only.

```sh
cd cloudflare-stats
./deploy.sh create   # secret + CronJob
./deploy.sh run      # one job right away, prints the JSON
```

Backfill one day: `kubectl -n monitoring create job cf-backfill --from=cronjob/cloudflare-stats` and add `STATS_DAY=YYYY-MM-DD` to the job env.

How the dashboards read the daily gauges: the value for day D is pushed every hour from D+1 00:10 until D+2 00:10. Panels use a 1-day step aligned to 00:00 UTC and read `last_over_time(m[1d] offset -2d)`, which lands on the finalized value of day D exactly once. "Yesterday" stats read the raw gauge. Monthly totals: `sum_over_time((last_over_time(ohm_cf_requests_daily[1d] offset -2d))[30d:1d])`. Do not use `max_over_time(m[1d])`: it mixes two days.

Every breakdown excludes Cloudflare's own `/cdn-cgi/` endpoints (the Web Analytics beacon posts to `/cdn-cgi/rum`, the JS challenge to `/cdn-cgi/challenge-platform/`): about 2.2M requests a day that never reach the origin and would otherwise look like POST edits on `api`. Their volume is kept in `ohm_cf_cdn_cgi_requests_daily`.

Each breakdown (by host, by agent, by status, host×status, ...) is its own sampled query scaled to the exact zone total, so two different breakdowns can disagree by a few percent. Compare series within one breakdown; use the zone totals when a number has to be exact.

The `cloudflared` pods in `ohm-tunnel` (see `ohm-deployment/hetzner/manifests/cloudflared-web.yaml`) also expose their own metrics on port 2000: `cloudflared_tunnel_total_requests`, `cloudflared_tunnel_response_by_code`. They give a live rate for the Hetzner tunnel only, with no per-host breakdown.

## EKS agent (while EKS is alive)

A minimal Prometheus in EKS (`values/prometheus.eks.yaml`) runs in **agent mode**: no Grafana, no Alertmanager, no local TSDB. It scrapes that cluster and pushes everything to the k3s Prometheus via `remote_write`. Metrics arrive labeled `cluster=aws-eks`. Remove it when EKS is shut down.

Before agent mode the pod ran a full server with a 1Gi limit. The WAL grew for weeks, the replay on start needed more than 1Gi, and the pod stayed OOMKilled for 60 days without ever sending data. Upgrading an existing install needs the old data volume wiped first (only the local WAL is lost, history lives in k3s):

```sh
kubectl -n monitoring scale deploy prometheus-server --replicas=0
kubectl apply -f manifests/prometheus-eks-wal-cleanup.yaml
kubectl -n monitoring logs -f prometheus-wal-cleanup
kubectl -n monitoring delete pod prometheus-wal-cleanup
./deploy_eks.sh create
```

Then in k3s Grafana check `up{cluster="aws-eks"}` has fresh samples.

The agent only keeps the series the dashboards and alerts read (`scrapeConfigs` in the values: API server job off, cadvisor and kubelet trimmed with `metric_relabel_configs`). If a new panel needs another `container_*` or `kubelet_*` metric, add it to the `keep` regex there, otherwise it never leaves EKS.

One-time setup in Cloudflare:

1. Public Hostname on the tunnel: `prometheus.openhistoricalmap.org` → `HTTP` → `prometheus-server.monitoring.svc.cluster.local:80`.
2. Zero Trust → Access → create an Application for `prometheus.openhistoricalmap.org` with a **Service Auth** policy, and create a **Service Token**. Use its credentials below.

Install the agent (kubectl context must be the EKS cluster):

```sh
# REMOTE_WRITE_URL and CF_ACCESS_* come from .env
./deploy_eks.sh create
```
